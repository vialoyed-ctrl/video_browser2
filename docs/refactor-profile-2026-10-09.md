# P1：Android Profile 性能基线

日期：2026-10-09。设备 PMB110 / Android 16 / API 36，id `BUPR8HWKLZTCHAPN`。当前显示模式记录为 120Hz；物理分辨率 1440×3200。设备原有辅助功能服务保持启用，未锁定温度、CPU/GPU 频率或系统后台负载。

## 方法

使用当前项目 ARM64 Profile 包，保留应用数据安装。启动时开启 `enable-dart-profiling=true`，通过 `flutter attach --profile --no-dds` 与 Dart VM Service 连接。

- 订阅 `Flutter.Frame`，记录真实 build/raster 微秒耗时。
- 用 VM timeline 的 Dart / Embedder / GC 记录排查方向。时间线环形缓冲约 32k 事件，仅覆盖窗口末尾；完整帧统计来自独立的 Frame 事件流，不从时间线累计外推。
- 首页每个窗口约 25 秒，共 27 次固定方向/距离滚动；页面、点击坐标均在设备上检查。
- 重复样本及修复后样本读取 `getMemoryUsage`，再通过诊断 GC 读取保留堆。Dart 堆不包含完整原生播放器/GPU内存；另存 Android meminfo。
- 原始数据、采集脚本与场景 XML 在 `work/handoff-validation/`，不提交带页面内容的截图/日志/时间线。

第一次抽屉自动测试使用返回键发生了误退出，isolate 被收集；该样本无效，已排除。重采改为点抽屉外区域关闭，结束时确认应用仍在前台。

本次 Android gfxinfo 在 Flutter Surface 场景报告总帧数 0、百分位为 4950ms 占位值，因此不使用其卡顿率或百分位，也不与交接中的旧安装版本样本作提升对比。

## 结论及限制

首页 build P95 较低，raster 存在接近/超过 120Hz 的 8.33ms 帧预算的样本。时间线末尾包含 SurfaceFrame 编码、GLES操作和语义树更新，后续应进一步区分 GPU/绘制和辅助功能语义更新开销。本轮没有因此改变裁剪、封面解码尺寸、辅助功能或 UI 样式。

8.131ms 与 8.033ms 的差异处于本轮已观察到的运行波动范围内。**没有证据证明播放器清理修复带来整体首页流畅度提升。** GC 后的差值也不能当作泄漏改善量。

播放页数据受原生视频帧节奏和纹理提交影响，不能直接按首页120Hz场景计算视频掉帧率。未采集 Perfetto、原生呈现PTS或真实首帧时间，不能声称播放页P95就是解码耗时或视听卡顿证据。

P1 已建立可复核的基线；搜索输入、分页、四站点切换、弱网、长时内存及重建热点仍待完整测量。未实施广泛 UI 架构改动。下一批 UI 候选必须先证明冗余重建/绘制来源，并保留画面、滚动位置、分页和辅助功能契约。
